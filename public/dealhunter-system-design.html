Revised architecture

Learn once. Run deterministically. Relearn on demand.

A product URL enters an LLM-assisted learning pipeline exactly twice in its lifecycle: during initial setup and when the user explicitly requests relearning. Every normal monitoring check executes a tested, versioned recipe with no LLM call.

Core decision DOM analysis and screenshot analysis generate a candidate monitor recipe. Automated browser tests must prove that recipe before activation. Ongoing checks run the compiled recipe at high speed.

Playwright screening

Captures DOM, visible text, accessibility representation, screenshot, and a sanitized network summary in the native TypeScript worker.

The compiled monitor recipe

The output is machine-executable configuration, not an LLM prompt.

  },

    }
  },
  "price": {
    "selector": "primary product price",
    "currency": "USD"
  },
  "challenge": {

    "action": "QUARANTINE"
  },
  "tests": ["identity", "scope", "disabled-cart", "conflicts"]

Identity before availabilityThe recipe must prove it is still looking at the expected SKU and product.
Scope before textSelectors are anchored to the product container and exclude recommendations.
Attributes before labelsEnabled and disabled state outrank visible “Add to cart” wording.
Precedence is explicitRetailer fulfillment data outranks SEO metadata and generic text.
Unknown is validA recipe may fail closed instead of manufacturing an availability answer.
04

Ongoing monitoring: no LLM

Every minute the worker executes the active recipe as ordinary deterministic code.

01ClaimAcquire listing lease and generation.
02AcquireHTTP, API, or pooled browser per recipe.
03BindVerify URL, SKU, title, variant, and seller.
04ExtractExecute stored fields and selectors.
05ValidateApply precedence, scope, and conflict rules.
06ConfirmRepeat only positive actionable candidates.
07CommitState transition, alert, and outbox atomically.
Performance consequence: the expensive LLM and screenshot work happens once during learning. Normal checks use cached recipe logic, pooled browsers, bounded selectors, and deterministic state transitions.
05

User-controlled adaptive scheduling

Scheduling is a first-class listing policy. Variability is used for safe load distribution and measured backoff, not for anti-bot evasion.

Default

System recommended

DealHunter learns from recent retailer success, timeout, rate-limit, and challenge history. Healthy retailers remain near the requested cadence; unhealthy paths back off automatically.

Exact

Fixed interval

The user chooses one interval, such as every 60 or 180 seconds. No variability is applied unless the retailer explicitly rate-limits the request.

Range

Bounded interval

The user chooses minimum and maximum bounds. Each next run is selected inside that range and the chosen duration is recorded with its reason.

Observed retailer healthSystem behaviorExample recommendationRecorded reason
Consistently successfulMaintain requested cadence with small bounded distributionApproximately 60 secondsLow challenge and failure rates
Elevated parse or network failuresReduce pressure and preserve worker capacityApproximately 120 secondsFailure rate crossed policy threshold

User-triggered relearning

A changed retailer never silently replaces the active recipe.

One-click user controlEvery listing exposes Relearn monitoring logic.
Versioned recipe diffShow changed selectors, fields, states, and tests before activation.
Shadow validationThe candidate recipe cannot create actions during evaluation.
Instant rollbackThe last-known-good recipe remains available.

09

Bot challenges and CAPTCHAs

The recipe learns how to detect challenges and choose approved alternate paths.

Safety boundary

DealHunter does not automate CAPTCHA solving, fingerprint masking, proxy rotation, or anti-bot bypass. Without human assistance, a challenge must become a controlled blocked state rather than a fabricated monitoring result.

REQUEST→ CHALLENGE_DETECTED→ STOP PATH→ APPROVED API / FEED?→ USE ALTERNATE or QUARANTINE
Detect

Challenge signatures

Status codes, challenge titles, interstitial DOM, CAPTCHA frames, empty application shells, and redirect patterns.

Recover

Approved alternatives

Official APIs, structured feeds, retailer notifications, previously authorized sessions where permitted, and longer cooldowns.

Remember

Retailer challenge memory

Store detection patterns, failure rates, allowed alternate methods, and recipe quarantine history.

interface ChallengeHandler {
  id: string;
  priority: number;
  supports(context): boolean;
  resolve(context): Promise<{
    action:
      | "RETRY_AFTER"
      | "USE_APPROVED_ALTERNATE"
      | "QUARANTINE";
    retryAfterSeconds: number;
    detail: string;
  }>;
}
Modular boundaryChallenge detection and response are isolated from retailer parsing and scheduling.
Safe defaultThe built-in provider applies cooldown or quarantine and records the reason.
Capability-gated extensionsAdditional organization-approved handlers can be registered without rewriting monitor recipes.
Audited outcomesEvery handler, action, retry duration, and alternate path is recorded.
10

Robustness and performance

The learn-once boundary makes rich setup compatible with one-minute monitoring.

Q

Per-retailer queues

A slow retailer cannot block another retailer’s checks.

B

Browser pools

Reuse Chromium processes while creating fresh isolated contexts.

H

DOM and response hashes

Skip unchanged enrichment and detect recipe drift cheaply.

C

Candidate-only confirmation

Double-check only results that could trigger an action.

L

Listing leases

Prevent overlapping scheduled and manual checks.

G

Generation control

Late browser results cannot overwrite newer state.

O

Transactional outbox

Committed transitions cannot lose their notification jobs.

R

Recipe rollback

Every active recipe retains its last-known-good version.

13

Acceptance criteria

The methodology is successful only if both setup quality and runtime discipline hold.

No LLM calls during normal checksAll one-minute monitoring uses compiled deterministic recipes.
Every recipe is executable and testedA model response alone is never activated.
Retailer learning is reusableNew products inherit known page archetypes and fixtures.
Relearning is versioned and reversibleCandidate recipes run in shadow mode before activation.
Challenges never look like stock resultsBlocked paths become quarantine or approved alternate acquisition.
Positive actions remain deterministicIdentity, state, price, and enabled controls must pass stored assertions.
Revised DealHunter architecture: LLM-assisted learning in steps one and three; deterministic monitoring in step two; reusable retailer knowledge in step four.
